# Finite State Machine（有限狀態機）：NPC 如何切換行為？

## 1. 什麼是有限狀態機？

Finite State Machine（FSM，有限狀態機）是一種描述「系統可能處於哪些狀態，以及輸入或事件如何造成狀態轉換」的模型。

一個基本 FSM 具有以下特性：

- 有一組固定的 **States（狀態）**。
- 系統在同一時間只能處於其中一個狀態。
- 系統會依序接收 **Inputs（輸入）** 或 **Events（事件）**。
- 每個狀態都有對應的 **Transitions（轉換）**；符合條件時，系統切換到指定狀態。
- 若目前狀態沒有定義對應的轉換，該輸入通常會被忽略。

例如，角色可能具有 `Patrol`、`Chase` 和 `Attack` 三個狀態。當角色正在巡邏並發現玩家時，巡邏狀態可以轉換到追逐狀態；當玩家離開攻擊範圍時，再轉回追逐或巡邏。這是將原始資料中的角色狀態概念套用到 NPC 的教學範例。

FSM 常用於：

- NPC 或敵人的巡邏、追逐、攻擊等行為。
- 玩家角色的站立、跳躍、蹲下與攻擊。
- 遊戲選單、對話流程及網路連線流程。

## 2. 為什麼不用許多布林旗標？

原始資料先展示了只使用一個布林旗標處理跳躍的程式。當角色開始跳躍後，程式可以設定 `isJumping = true`，並在角色落地後重設旗標。

但加入蹲下、潛水或蓄力攻擊後，可能需要多個布林旗標，例如：

- `isJumping`
- `isDucking`
- `isDiving`
- `isCharging`

多個旗標會產生一些無效組合，例如角色同時跳躍又蹲下。它們也可能讓各種輸入與判斷分散在多個方法中，增加除錯與維護成本。

FSM 的核心做法，是用「一個目前狀態」取代互相獨立的行為旗標。這能確保角色處於一個明確且有效的狀態。

## 3. Enum 與 Switch 的簡單實作

最簡單的實作方式是使用列舉（`enum`）表示狀態，再使用 switch 語句處理每個狀態：

```csharp
enum NPCState
{
    Patrol,
    Chase,
    Attack
}

NPCState state = NPCState.Patrol;
```

概念上的輸入處理可以寫成：

```csharp
switch (state)
{
    case NPCState.Patrol:
        if (PlayerDetected())
        {
            state = NPCState.Chase;
        }
        break;

    case NPCState.Chase:
        if (PlayerInAttackRange())
        {
            state = NPCState.Attack;
        }
        else if (PlayerLost())
        {
            state = NPCState.Patrol;
        }
        break;

    case NPCState.Attack:
        if (!PlayerInAttackRange())
        {
            state = NPCState.Chase;
        }
        break;
}
```

這個寫法集中處理單一狀態，不需要保留互相衝突的多重布林旗標。原始資料指出，使用 enum 與 switch 的實作簡單、適合較小型的問題。

需要注意的是，上方程式是依照原始 FSM 概念整理的 C# 教學範例；實際 Unity 專案中的偵測與移動 API 須另外依專案實作。

## 4. 狀態中的程式資料與行為

當 FSM 出現只在特定狀態才需要的資料時，例如角色在蹲下時累積蓄力時間，該資料應盡量與該狀態放在一起。

原始資料指出：

- 若把蓄力時間放在角色主物件，即使角色不處於蹲下狀態，資料仍然存在。
- 若把蓄力時間移入蹲下狀態物件，資料的用途更明確。
- 當角色進入該狀態時應初始化資料；離開時可以釋放或重設資料。

這個原則有助於理解 FSM 不只是切換數字或列舉，也是在不同狀態間管理行為與暫存資料。

## 5. State Pattern：每個狀態一個物件

當 switch 語句變得很長時，可以使用 Gang of Four 的 State Pattern（狀態模式）。

核心做法是：

1. 定義一個所有狀態都要實作的介面或基底類別。
2. 為每個狀態建立獨立類別。
3. 每個狀態類別負責處理該狀態可接受的輸入與行為。
4. 角色保留一個指向目前狀態物件的參考。
5. 狀態轉換時，角色把參考切換到另一個狀態物件。

例如：

```text
NPCState
  ├─ PatrolState
  ├─ ChaseState
  └─ AttackState

NPC.state -> 目前狀態物件
```

以概念方式表示委派（Delegation）：

```text
NPC 收到輸入
    -> 目前 State 處理輸入
    -> State 決定是否切換
    -> NPC 更新目前 State
```

原始資料強調，這不是規定所有 FSM 都必須使用物件導向方法；如果問題簡單，`enum` 加 `switch` 可能就足夠。

## 6. Enter Action 與 Exit Action

進入狀態時，FSM 可以執行 **Entry Action（進入動作）**；離開狀態時，則可以執行 **Exit Action（離開動作）**。

常見用途包括：

- 進入巡邏狀態時啟動巡邏路線。
- 進入追逐狀態時播放警戒動畫。
- 進入攻擊狀態時重置攻擊冷卻時間。
- 離開受傷狀態時移除受傷效果。
- 無論來自哪個前一狀態，只要進入相同狀態，就執行相同的進入動作。

Exit Action 則適合處理離開狀態前需要清除的資料或效果，例如停止正在執行的計時器。

## 7. 限制：簡單 FSM 容易組合爆炸

FSM 的優點是結構明確，但它不適合無限制地堆疊所有能力組合。

原始資料以角色可攜帶武器為例：若同時需要「站立、跳躍、蹲下」與「持有武器、未持有武器」，將所有組合放在同一台 FSM，可能需要：

```text
站立、持槍站立、
跳躍、持槍跳躍、
蹲下、持槍蹲下...
```

若主行為有 n 種狀態，攜帶裝備有 m 種狀態，同一 FSM 的組合可能接近 n × m，而不是 n + m。

更好的方式可能是使用 **Concurrent State Machines（並行狀態機）**：讓移動與裝備分成兩台 FSM，各自處理自己的狀態，再由遊戲邏輯協調兩者。例如角色跳躍時禁止開槍，就可以由協調邏輯檢查另一台 FSM 的目前狀態。

## 8. 進階狀態結構

### 階層式狀態機（Hierarchical State Machine）

Hierarchical State Machine 可以讓相似狀態共享共同行為。

例如：

```text
OnGround
  ├─ Stand
  ├─ Walk
  └─ Run
```

站立、走路與跑步都位於地面時，共同支援跳躍或蹲下。子狀態處理自己的輸入；若沒有處理，則交給上層超狀態（Superstate）處理。

這可減少重複轉換與重複程式。

### 堆疊式狀態機（Pushdown Automaton）

基本 FSM 沒有「上一個是什麼狀態」的歷史記憶。若角色在開槍後需要自動回到開槍前的狀態，直接使用基本 FSM 可能需要為每個來源狀態建立重複的開槍狀態。

Pushdown Automaton 使用狀態堆疊：

- Push：保留目前狀態並切換到上層的新狀態。
- Pop：移除目前狀態並回到下一個原本的狀態。

例如，角色正在巡邏時被中斷，FSM 可以將「巡邏」保留在堆疊下方，先切換到「受傷」，完成後再 Pop 回巡邏。這是一種處理暫時中斷、稍後回復的方式。

## 9. FSM 在遊戲 AI 中的適用情境

FSM 適合處理：

- 行為可以明確分成少量選項的實體。
- 狀態會在輸入或事件後轉換。
- 轉換規則容易畫成流程圖或狀態表。
- 不需要複雜的多步規劃或大量動態組合。

對初學者而言，FSM 特別適合建立：

- 不發現玩家時巡邏，發現後追逐，進入距離後攻擊。
- 過場或教學流程中的互動步驟。
- 選單、網路連線、動畫狀態與按鍵操作。

當行為需要大量重疊條件、動態規劃或複雜優先順序時，可以再評估 Behavior Tree（行為樹）或 Planning System（規劃系統）。

原始資料提到這類工具是處理複雜遊戲 AI 的另一條發展方向，但不表示所有 FSM 都必須立即改成其他架構。

## 10. 初學者實作建議

設計一個 NPC FSM 時，可以依序完成：

1. 列出所有可能狀態，例如巡邏、追逐、攻擊與撤退。
2. 為每個狀態畫出可執行的行為。
3. 列出觸發轉換的輸入或條件。
4. 用流程圖確認所有合法轉換。
5. 先用 enum 與 switch 實作最小版本。
6. 當狀態邏輯變得重複或難以維護，再考慮 State Pattern。
7. 當功能與能力彼此正交時，使用並行或階層式 FSM 分拆問題。
